# Rollback - 018: Meetings Section-Scoped Access Control

Run `supabase/rollback-meetings-section-scope.sql` only to undo the UAT correction narrowing meeting visibility/edit rights from a blanket "any supervisor in the org" rule to section/command/department-scoped access (`supabase/patch-meetings-section-scope.sql`).

This rollback modifies existing function bodies rather than dropping wholly new objects: `can_manage_meeting()` and `can_view_meeting()` are restored to their exact pre-patch bodies (the blanket `is_supervisor_or_above()` term, no section branch), and `create_meeting()`/`update_meeting()`/`create_recurring_meeting()` are restored without their new `p_section_id`/`p_clear_section` parameters. `meetings.section_id` and `meeting_series.template_section_id` are then dropped.

The rollback unconditionally refuses if any meeting has `section_id IS NOT NULL` or any recurring series has `template_section_id IS NOT NULL` — once a real meeting has been tagged to a section (whether relied on for this access-control feature or just used as an informational "on behalf of" label), dropping the column would silently destroy that data. Clear those values first if you are certain, or keep this patch applied.

Verified procedure: applied the patch to a database with the full prior Meetings foundation/lock/recurring chain; confirmed `can_manage_meeting`/`can_view_meeting` correctly grant access to same-section staff and command/department-scoped `user_assignments` holders while leaving `is_admin()`/super-admin/creator/participant access unchanged, and that a locked meeting still rejects everyone except creator/admin/super-admin; ran the rollback with no `section_id` set anywhere — succeeded cleanly, restoring the exact prior blanket-supervisor behavior; separately tagged one meeting with a real `section_id`, then attempted rollback — refused, exactly as designed, with the patch and the tagged row left completely intact; reapplied the patch after a clean rollback and reran validation — passed.
