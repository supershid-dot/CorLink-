# Rollback - 017: Workflow Delegation and Substitution Foundation

Run `supabase/rollback-workflow-delegation-substitution-foundation.sql` only to remove CAP-002 Phase 5.1 (delegation and substitution persistence foundation) while retaining the entire approved Phase 1 through 4.3 workflow engine.

The rollback is transactional and uses no `CASCADE`. Every object this milestone created is wholly new (no existing function body was modified by this patch), so the rollback restores nothing — it drops, in dependency order, the four new tables (`workflow_delegations`, `workflow_delegation_events`, `workflow_substitutions`, `workflow_substitution_events`), all ten public RPCs (`create_workflow_delegation`, `accept_workflow_delegation`, `reject_workflow_delegation`, `revoke_workflow_delegation`, `get_workflow_delegation`, `list_workflow_delegations`, `create_workflow_substitution`, `revoke_workflow_substitution`, `get_workflow_substitution`, `list_workflow_substitutions`), and the six private helper/trigger functions (`workflow_delegation_visible_to_caller`, `workflow_substitution_visible_to_caller`, `can_manage_workflow_delegation_scope`, `workflow_reject_terminal_delegation_mutation`, `workflow_reject_delegation_event_mutation`, `workflow_reject_terminal_substitution_mutation`). The `btree_gist` extension is deliberately **not** dropped: it is also a dependency of the already-approved, separate `patch-rooms-booking-foundation.sql`, and this patch does not own it exclusively.

The rollback unconditionally refuses if any row exists in `workflow_delegations`, `workflow_delegation_events`, `workflow_substitutions`, or `workflow_substitution_events` — this milestone created wholly new tables with no prior history possible, so any row present at rollback time is necessarily real, created work that a permissive rollback would silently destroy. This mirrors the Phase 1 (`rollback-workflow-backend-foundation.sql`) "refuse if any row exists" precedent, not the "protect only real activated work" precedent used by later phases whose rollback restores a prior function body — there is no prior body here to protect a fallback path for.

The verified procedure was: apply the Phase 5.1 patch to a fresh Phase 1 through 4.3 chain; confirm the structural validator and full 35-scenario behavioral suite pass; apply the rollback with no delegation/substitution rows present — succeeded cleanly; run `supabase/validate-workflow-delegation-substitution-foundation-rollback.sql` — passed; separately, create one real delegation via `create_workflow_delegation`, then attempt rollback — refused, exactly as designed, with the full Phase 5.1 schema and the created row left completely intact; build a **true independent pre-5.1 baseline** (Phase 1 through 4.3 chain only, this patch never applied) and diff the complete `public`-schema function name list between the rolled-back database and that baseline, excluding only objects owned by the `btree_gist`/`dblink` extensions (deliberately preserved for the reasons above, and — in `dblink`'s case — an artifact of the disposable test harness's own concurrency-test setup, not of this patch) — **zero difference** in every case; reapply the patch to the rolled-back database and rerun the structural validator and full 35-scenario behavioral suite — both passed, confirming clean reapplication.
