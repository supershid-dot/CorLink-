# CAP-002 Phase 4.3 — Workflow Engine Stabilization & Production Readiness

## Scope

This is a stabilization milestone, not a feature milestone. It verifies the complete workflow engine built across Phases 1 through 4.2 against docs/60 through docs/71, hardens exactly the genuine defects that verification surfaces, and records the engine's production-readiness posture. It introduces no new node type, no new workflow capability, no delegation, timers, adapters, or notifications, and no architecture change.

## Architecture summary

The engine is a single-token, event-sourced graph executor. A workflow definition is an immutable, content-hashed, published JSON payload (`schema_version` 1 or 2) of `start`/`approval`/`end` nodes (Version 1) plus `gateway_exclusive` nodes and condition-bearing edges (Version 2), validated in full at publish time by `canonicalize_workflow_definition_payload`. An instance advances one token at a time through the graph; every node entry, decision, and routing choice is recorded as an immutable, contiguously-sequenced, causation-chained row in `workflow_events`, and every mutating command is idempotent by caller-supplied key, replaying its own root event's metadata rather than re-executing on retry. Two shared, private helper functions — `workflow_enter_downstream_node` (real graph advancement) and `workflow_peek_final_graph_target` (replay-metadata computation) — contain the entire "what happens when the token reaches this node" logic; every public command (`workflow_transition_instance`, `workflow_advance_graph_step`, `decide_workflow_work_item`) calls into these two helpers rather than duplicating node-entry logic, so `end`-completion, approval-round-opening, zero-candidate-skip, and gateway-routing behavior can never diverge between entry points.

Authorization is two-tier: `can_manage_workflow_instance()`/`can_manage_workflow_definition()` gate lifecycle and definition commands (manager/owner boundary); `work_item.assigned_to = auth.uid()` gates decisions (the exact assigned voter, a deliberately different and narrower boundary per docs/63). Every table carries a single SELECT-only RLS policy; every mutating operation goes through a `SECURITY DEFINER` function with a pinned `search_path` that performs its own authorization check before touching any row — RLS is never relied on to protect a write path, since none exists at the table-grant level (`information_schema.role_table_grants` confirms zero non-SELECT grants to `anon`/`authenticated` on any workflow table). Every append-only table (`workflow_events`, `workflow_decisions`, `workflow_definition_versions`, and terminal-state rows of `workflow_approval_rounds`/`workflow_approval_positions`) carries a `BEFORE UPDATE OR DELETE` trigger that unconditionally rejects the mutation.

## Implemented capabilities

- **Lifecycle**: create/publish definitions (Version 1 and Version 2); create/start/suspend/resume/cancel/complete instances; legacy inert-instance behavior preserved unchanged for non-executable payloads.
- **Graph execution**: `start` → `approval`/`gateway_exclusive` → `end`, with any number of consecutive gateway hops or zero-candidate optional-approval skips resolved synchronously within a single command via the shared bounded loop (defensive cap: 32 immediate entries per command).
- **Approval execution**: required/optional nodes; parallel/sequential delivery; unanimous/majority decision rules with configurable `minimum_approvals`; abstention policy; per-decision-code comment policy; manager-gated blocked/unavailable candidate counts; zero-candidate optional-node skip-and-continue.
- **Routing execution**: `gateway_exclusive` condition evaluation over the closed docs/69 operator registry (`equals`, `not_equals`, `in`, `not_in`, four comparison operators, `is_null`/`is_not_null`) across six value types; deterministic ascending-priority branch selection with a mandatory default edge; instance-variable read/write foundation (`set_workflow_instance_variable`).
- **Events, replay, and concurrency**: contiguous per-instance event sequencing; causation chains rooted at each command's own canonical event; idempotency-key replay for every mutating command, each reading its own root event's metadata back rather than re-deriving state; a single global advisory-lock-then-row-lock order reused identically by every command, serializing all concurrent access to one instance without a dedicated lock tier per feature.

## Deferred capabilities (unimplemented, by design)

Parallel split, synchronizing merge, and multi-token execution; decision delegation, substitution, and escalation; timers and scheduled transitions; notifications; module/adapter variable sources; boolean condition composition (`AND`/`OR`/`NOT`); any frontend or workflow designer. None of these were touched, stubbed, or partially implemented by this or any prior phase — the single-token, closed-operator-registry model is a deliberate scope boundary stated in docs/69 and preserved throughout.

## This milestone's findings

A read-only audit compared every claim in docs/67–71 against the actual, currently-committed function bodies (prioritizing authorization, event confidentiality, validation boundaries, idempotency-replay contracts, lock ordering, and event sequencing/causation). One genuine defect was found and independently re-verified against the true source before any fix was written:

**`decide_workflow_work_item`'s idempotency-replay comparison omitted the two expected-lock-version fields.** docs/67 states its replay check has "identical semantics to every other command in this codebase," and its two closest siblings (`workflow_transition_instance`, `workflow_advance_graph_step`) both reject a replay whose expected lock version differs from the original call's. `decide_workflow_work_item` compared only `work_item_id`/`decision_code`/`comment`, so a command_id replayed with the same decision but different (stale or arbitrary) expected lock versions silently returned the original result instead of the documented `22023` rejection. No data corruption was possible (the replay path returns before any further mutation), but the omission masked exactly the client-side-inconsistency signal this comparison exists to surface. Confirmed exploitable against the pre-fix code with a direct reproduction, then fixed narrowly: `decision_recorded`'s metadata now additionally records the caller's expected lock versions, and the replay comparison now includes them, mirroring the sibling commands' own pattern exactly. Re-verified fixed with the same reproduction, plus a new permanent regression scenario (`test-workflow-approval-decision-engine.sql` scenario 19) proving both the rejection and that a true replay with identical lock versions still succeeds.

Everything else this milestone verified came back clean:

- **Rollback/reapply chain**: the full reverse-rollback chain (Phase 4.2 → Phase 1) and full forward-reapply chain were exercised end-to-end against a disposable database. All ten phases' own rollback validators passed in strict reverse order (two apparent failures at the outermost Phase 1 boundary were traced to the isolated test database lacking sibling-CAP tables — `task_dependencies`, `task_relationships` — owned by an already-merged, unrelated CAP outside this milestone's scope, not a defect in any CAP-002 object). The reapplied chain was confirmed structurally identical to the originally-built chain via all nine forward structural validators.
- **Large mixed-graph stress test**: a single instance driven through a 12-node graph interleaving three `gateway_exclusive` nodes and two real, multi-candidate approval rounds completed correctly, with event sequencing perfectly contiguous over 39 events, every causation_id resolving to a real event, zero orphaned work items/tokens/steps/rounds after completion, and a decision from early in the run still replaying correctly (identical result, zero new events) after the instance had advanced three more gateways and one more decision past it.
- **Security review**: every `workflow_*`/decision/gateway function confirmed `SECURITY DEFINER` with pinned `search_path` (the small number of exceptions are genuine `TRIGGER`-return-type functions, which do not need `SECURITY DEFINER`, and one pure-scalar-computation helper with no table access); the `anon` EXECUTE grants found on two trigger functions were confirmed empirically inert (Postgres refuses any non-trigger invocation of a trigger function outright); RLS enabled with exactly one SELECT-only policy on every one of the 12 workflow tables; zero direct write grants to `anon`/`authenticated` on any workflow table; every append-only table's immutability trigger confirmed to unconditionally reject UPDATE/DELETE by direct inspection of the trigger body.
- **Performance**: re-measured against the full patched chain — no regression from the hardening fix. Representative figures from this session's disposable-Postgres runs: single-hop advancement ~5–20 ms; a 200-node/395-edge definition create+canonicalize ~150–180 ms; a 25-hop consecutive skip or gateway chain resolved synchronously ~20–44 ms; a maximal 16-branch gateway ~6–10 ms; any single operation against an instance whose event history already has 100,000 rows ~1–9 ms, confirmed via `EXPLAIN (ANALYZE, BUFFERS)` to use the existing sequence/correlation indexes rather than a sequential scan. No index was added — every dimension measured stayed within the same order of magnitude the corresponding phase originally recorded.

## Production readiness

Within its stated scope (single-token graph execution with `approval` and `gateway_exclusive` nodes), the engine is production-ready: every command is idempotent and replay-safe under concurrency; authorization is centralized and independently re-verified in this milestone; history is append-only and immutable at the trigger level; rollback exists and is proven for every phase, with each rollback's refusal or non-refusal policy independently reasoned and documented; and the one genuine defect this stabilization pass found was narrow, non-corrupting, and is now fixed, tested, and covered by a permanent regression scenario.

## Known limitations

- No parallel split, synchronizing merge, or multi-token execution — one active token per instance, by design.
- No delegation, substitution, escalation, timers, or notifications.
- No `module_variable` condition source — only `instance_variable` and static literals.
- No boolean condition composition — one atomic condition per gateway edge.
- No frontend or workflow designer.
- Phase 1's rollback validator (`validate-workflow-backend-foundation-rollback.sql`) asserts the presence of sibling-CAP tables (`task_dependencies` in its own check, `task_links` in the forward validator's check) that live in a different, already-merged CAP outside this module's own patch chain — a naming inconsistency between those two pre-existing validator files noted during this milestone's rollback-chain stress test, unrelated to any CAP-002 runtime behavior and left unchanged as out of this milestone's scope.

## Future phases

Any of the deferred capabilities above, if ever taken up, should each get their own architecture document (following the docs/69 precedent for Version 2 routing) before implementation — this milestone changes nothing about that discipline. No specific future phase is scheduled by this document.
